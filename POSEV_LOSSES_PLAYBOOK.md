## 0. Модель «посевов»: ДВЕ независимые оси + граница 01.05.2026

Посевы устроены так, что **расход и воронка считаются из РАЗНЫХ источников и разными механизмами**.
Сравнивать их «в лоб» (заявка против заказа) нельзя — это две оси, которые пересекаются только
через слабый ключ разметки (UTM поста).

### Ось A — РАСХОД / ЗАКАЗЫ (только ≥ 01.05.2026)
- Источник: `public.local_telega_in_orders` (1 строка = 1 заказ-пост на бирже Telega.in), `status='complete'`, `created_at >= '2026-05-01'`.
- Код: `step10_crop_targeting/load_telega_in_orders.py` (md5 `e51d885`).
- Матч заказ↔лид = **строгое РАВЕНСТВО 5 полей** (LATERAL, L277-286): `effective_domain` + `utm_campaign` + `lpad(btrim(utm_content),8,'0')` + `lower(btrim(utm_source))` + `lower(btrim(utm_medium))`.
- `utm_content` = **дата поста** в формате `DDMMYYYY` (НЕ дата заявки/визита). Это идентификатор-равенство, не сравнение дат.
- `effective_domain` = host из `post_links` jsonb→>0 (fallback `order_project_name`; редиректоры `telega.io`/`max.ru`/`t.me` → fallback).
- Контроль расхода после мая: **214 заказов / 2 181 280.24 ₽** (matched 102/1 637 123.31 = 75.05% + orphan 112/544 156.93 = 24.95%).

### Ось B — ВОРОНКА (направление='посевы' в `big_analytics_full`)
- Код: `step10_crop_targeting/load_crop_to_big_analytics.py` (md5 `d7fb82d`), **две ветви по дате**:
  - **до мая** (`Дата < 2026-05-01`): `INSERT_GSHEETS_SQL` из `gsheets_crop_targeting_account_leads`. Матч лид↔размещение = nearest-prior placement по 3 ключам (utm_campaign→`utm утвержденная` через мост `pravilo_utm`; домен лида = `Сайт` размещения; placement_date ≤ created_date, delta ≤ 90 дней, DISTINCT ON lead_id). **`utm_content` тут НЕ участвует** → метки `00000000` безвредны.
  - **после мая** (`Date >= 2026-05-01`): `INSERT_API_SQL` из `crop_targeting_api_telegain_lead` — берёт ВСЕ строки таблицы без фильтра по матчу.

### ⚠️ Ключевая механика (доказана кодом)
**После мая воронка посевов строится ОТ РАСХОДА/ЗАКАЗА, а НЕ от заявки.** Таблица `crop_targeting_api_telegain_lead` = `local_telega_in_orders` (1 строка = заказ) LEFT JOIN LATERAL агрегат лидов по 5-полевому ключу. Метрики лидов = `COALESCE(kol_vo_zayavok,0)`. Значит:
- несматченный **ЗАКАЗ** → строка с `cost>0 / kol_vo=0` (расход без заявок — **норма**);
- несматченная **ЗАЯВКА** (нет заказа по 5 полям) → **строки не порождает вообще** → её нет в `big_analytics_full` даже с `cost=0` → **полная потеря из воронки** (это категория 4 ниже).

Контраст: **до мая** строка тоже от размещения, но `utm_content` не ключ → лиды с `00000000` учитываются (пример: 12 апрельских лидов avtoworld-kuban.ru / chp_majkop → 1 строка cost 17 772.30 / kol 12).

### 1. Telegram NOT IN без домена (хрупкость #1) — фикс = ЗАДВОЕНИЕ ⚠️ важнейшая карточка

- **Что это / симптом.** В `step3_build_sources/step3.py` функция `_add_telegram_to_crop_sql` (L972-980) использует **голый `NOT IN (SELECT UTM / "utm утвержденная" FROM ...pravilo_utm)` БЕЗ привязки к домену**. `pravilo_utm` не содержит колонки домена (только UTM ↔ «utm утвержденная») — это корень хрупкости. Фильтр работает глобально по метке: если метка есть в `pravilo_utm` для ЛЮБОГО домена, telegram-лид вырезается, даже если на ЕГО домене метка не утверждена. Контраст: соседняя `_add_social_posev_to_crop_sql` (L1126) уже исправлена на `NOT EXISTS` с JOIN по домену.
- **Возможный масштаб.** Голый `NOT IN` вырезает **865 telegram-posev-лидов** (19 доменов / 107 меток). Из них **«37 зря вырезанных»** (8 доменов / 9 меток / 14.01–05.04, 7 визитов, 0 продаж) — метка есть в `pravilo_utm` глобально, но не в реестре `gsheets_crop_targeting_account` для своего домена.
- **Как проверять** (кандидаты на «зря вырезанные» + проверка, не задвоятся ли они):
```sql
-- (А) telegram-posev-лиды, вырезаемые голым NOT IN, но имеющие метку на СВОЁМ домене
WITH cut AS (
  SELECT l.id, lower(trim(ld.name)) AS domain, l.utm_campaign,
         to_char(l.created_date,'YYYY-MM-DD') AS dt
  FROM local_leads_all l
  JOIN local_domains ld ON ld.id = l.domain_id
  WHERE l.utm_medium = 'posev' AND lower(l.utm_source) = 'telegram'
    AND coalesce(l.utm_campaign,'') <> ''
    AND ( l.utm_campaign IN (SELECT "UTM" FROM gsheets_crop_targeting_account_pravilo_utm)
       OR l.utm_campaign IN (SELECT "utm утвержденная" FROM gsheets_crop_targeting_account_pravilo_utm) )
)
SELECT c.domain, c.utm_campaign, count(*) AS leads,
       -- метка утверждена для ЭТОГО домена в account_leads?
       EXISTS (SELECT 1 FROM gsheets_crop_targeting_account_leads al
               WHERE lower(trim(al."Сайт")) = c.domain
                 AND al."utm утвержденная" = c.utm_campaign) AS in_own_acctleads
FROM cut c GROUP BY 1,2 ORDER BY leads DESC;
```
```sql
-- (Б) пересечение тех же меток с уже учтёнными лидами ДО мая (gsheets-ветка воронки)
-- если совпадает domain+created_date+kol_vo — лиды УЖЕ в воронке, фикс задвоит
SELECT lower(trim(al."Сайт")) AS domain, al."utm утвержденная" AS camp,
       al."Дата", al."Кол-во лидов"
FROM gsheets_crop_targeting_account_leads al
WHERE lower(trim(al."Сайт")) = :domain AND al."utm утвержденная" = :camp;
```
- **Как понять РЕАЛЬНАЯ ли это потеря.**
  - **ДО мая — потери НЕТ, фикс ВРЕДЕН (задвоение).** Доказано: по всем 11 связкам «37 зря вырезанных» `in_own_acctleads = TRUE` и `tg_cut_leads == acctleads_kolvo_sameday` (те же физ. лиды: chp_tolyatti3=3, tvoy_stvrp4=4, mihaylovsk2=2, obychn2=2 и т.д.). До мая воронка строится из `gsheets_crop_targeting_account_leads` — **эти 37 уже в воронке через gsheets-источник**. Подтверждено в `big_analytics_full`: на тех же домен+дата `posev_zayavok_full > 0`. Метка не в реестре `account` (по «utm утвержденной»), но в `account_leads` (менеджер занёс через leads-джойн) — это эффект raw-вариантов слага (`obychn_stvrp`→`obychnyi_stvrp` и т.п.). Telegram-ветка `_add_telegram` агрегирует по `domain+created_date` ПОВЕРХ gsheets → исправление `NOT IN`→`NOT EXISTS` вернёт их вторым экземпляром = **ЗАДВОЕНИЕ**. Тест: фикс `social`-стиля (NOT EXISTS account_leads + kol_vo>0) вернул бы лишь 1 из 37.
  - **Фикс реально нужен ТОЛЬКО после мая**, где telegram-ветка — единственный источник этих лидов, И **только после проверки пересечения с `crop_targeting_api_telegain_lead`** (чтобы не задвоить с осью расхода). Условие реальной потери: лид после мая + метка на своём домене + НЕ присутствует ни в gsheets-ветке (до мая её нет), ни в api-ветке (нет заказа с тем же 5-полевым ключом).
- **Как решить.**
  - **ДО мая: НЕ ПРИМЕНЯТЬ фикс** — 0 однозначно к возврату, риск задвоения 37 лидов.
  - **После мая (если возникнет):** переписать `_add_telegram_to_crop_sql` (step3.py L972-980) с `NOT IN` на `NOT EXISTS` c JOIN по домену (как `_add_social` L1126), НО с дополнительным `NOT EXISTS` по `crop_targeting_api_telegain_lead` (5 полей). Риск: golden + двойной учёт с осью расхода → обязательная golden-сверка + проверка инварианта `korr ≥ kval ≥ priezd ≥ prodazhi`.

### 2. orphan-расход: `utm_content` не совпал (≈273 594 ₽)

- **Что это / симптом.** Заказ Telega есть, лид по домену+кампании есть, но `utm_content` (дата поста) не совпадает. Вкладка `matchable_другая_дата_после_мая` / причина в `orphans_расход_после_мая` = `utm_content_заказа_не_найден_в_лидах_другой_пост_или_пустой`.
- **Возможный масштаб.** **39 заказов / 273 594.12 ₽**. Подклассы: **A1 = 16 / 144 715.14** (лид с реальной, но ДРУГОЙ датой поста); **A2 = 22 / 126 880.98** (лид с `utm_content='00000000'` — дата поста потеряна в разметке); **канал_дрейф = 1 / 1 998** (лид только по 2 полям домен+camp).
- **Как проверять:**
```sql
-- расход-сироты после мая, ослабление ключа до 4 полей (без utm_content)
WITH tio AS (
  SELECT d.*, /* effective_domain вычислен как в load_telega_in_orders */ TRUE AS _ok
  FROM local_telega_in_orders d
  WHERE d.status='complete' AND d.created_at >= '2026-05-01'
), leads4 AS (
  SELECT lower(trim(ld.name)) AS domain, l.utm_campaign,
         lower(btrim(l.utm_source)) AS src, lower(btrim(l.utm_medium)) AS med,
         array_agg(DISTINCT lpad(btrim(l.utm_content),8,'0')) AS contents
  FROM local_leads_all l JOIN local_domains ld ON ld.id=l.domain_id
  WHERE coalesce(l.utm_campaign,'')<>'' GROUP BY 1,2,3,4
)
-- orphan по 5 полям, НО лид по 4 полям существует ⇒ это категория «utm_content не совпал»
SELECT count(*) AS orders, round(sum(t.total_price),2) AS spend
FROM tio t JOIN leads4 g
  ON g.domain = t.effective_domain AND g.utm_campaign = t.utm_campaign
 AND g.src = lower(btrim(t.utm_source)) AND g.med = lower(btrim(t.utm_medium))
WHERE lpad(btrim(t.utm_content),8,'0') <> ALL (g.contents);  -- ⇒ 39 / 273594.12
```
- **Как понять РЕАЛЬНАЯ ли это потеря.** Это **by-design зеркало**, НЕ потеря FDW.
  - **A1** (16 / 144.7к): дельта между датой закупки и датой поста лида **min 3 / max 25 / avg 13.1 дней** (распределение: d0=0, d1-2=0, d3-7=2, d8-14=9, d15-30=5). Это НЕ лаг заявки 1-2 дня — это **разные посты одной кампании**: расход на пост X, а размеченные лиды пришли с поста Y той же кампании. Выравниванием дат НЕ чинится (нечего выравнивать — посты разные). Пример: order 2368618 avtoworld chp_krasnodara_max закупка 29052026, лиды [18052026, 26052026].
  - **A2** (22 / 126.9к): у лидов `utm_content='00000000'` — дата поста утрачена в разметке ссылки. Выравнивать нечего.
  - **Критерий реальной потери (не выполняется здесь):** была бы потеря, если бы дельта = 1-2 дня (тот же пост, лаг CRM) — таких **0 заказов**.
- **Как решить.** Кодом не чинится (разные посты / `00000000`). Процесс: **дисциплина разметки постов** — ставить корректный `utm_content=DDMMYYYY` поста на стороне Telega.in/разметчика, тогда заказ и лид сойдутся по 5-полевому ключу. До этого — оставить как информативную категорию (расход-сторона зеркала), НЕ считать ошибкой.

### 3. orphan-расход: метка не найдена на домене (≈269 923 ₽)

- **Что это / симптом.** Заказ Telega есть, но лида НЕТ даже по ослабленному ключу домен+кампания. Причина в `orphans_расход_после_мая` = `метка_не_найдена_в_лидах_на_домене`. Это вторая (не-matchable) половина orphan-расхода.
- **Возможный масштаб.** **72 заказа / 269 923.45 ₽** (+ 1 / 639.36 key_defect — заказ `carnew-vlg.ru` 2356647 с пустыми UTM, закупка без разметки). 72 + 39 (категория 2) + 1 = 112 / 544 156.93 (весь orphan-расход) ✓.
- **Как проверять:**
```sql
-- расход-сироты, где НЕТ лида даже по домену+кампании
WITH tio AS (SELECT * FROM local_telega_in_orders WHERE status='complete' AND created_at>='2026-05-01'),
leads2 AS (
  SELECT lower(trim(ld.name)) AS domain, l.utm_campaign
  FROM local_leads_all l JOIN local_domains ld ON ld.id=l.domain_id
  WHERE coalesce(l.utm_campaign,'')<>'' GROUP BY 1,2)
SELECT count(*) AS orders, round(sum(t.total_price),2) AS spend
FROM tio t
WHERE NOT EXISTS (SELECT 1 FROM leads2 g
                  WHERE g.domain = t.effective_domain AND g.utm_campaign = t.utm_campaign)
  AND coalesce(t.utm_campaign,'') <> '';  -- ⇒ 72 / 269923.45
```
- **Как понять РЕАЛЬНАЯ ли это потеря.** Граница тоньше, чем у категории 2.
  - **НЕ потеря (дрейф слага / другой канал):** если на том же домене+периоде расход и заказы ЕСТЬ под ДРУГИМИ слагами той же закупки — это семантический дрейф слага (метка поста ≠ слаг канала), та же природа A1. Доказано для max/tg-меток: точной метки в заказах нет, но `orders_same_src` 21-25 на домене.
  - **НЕ потеря (вне Telega):** VK-метки (`*_vk*`) — Telega.in VK НЕ закупает совсем (в `local_telega_in_orders` `utm_source`: telegram 702 / max 540 / пусто 234 / m 1 / yandex 1, **VK = 0**). Лид с VK-поста = органика/закупка VK другим каналом → расхода в Telega быть не должно → НЕ потеря FDW.
  - **РЕАЛЬНАЯ потеря привязки:** заказ есть (деньги ушли), а на домене НЕТ ни одного посевного лида с этой кампанией ни в каком слаге, при этом `utm_source` заказа = telegram/max (Telega реально закупала) → закупка на пост, с которого размеченный лид не пришёл/не размечен. Это потерянная привязка расход→результат.
  - Контроль здоровья FDW: 1478 заказов, свежесть 05-06.06, 24 домена, статус `complete`; cross-domain утечки 0 (orphan-заказ не имеет лида на другом домене) → orphan-расход genuine, не коллизия.
- **Как решить.** Частично процессом (разметка постов + единый словарь слагов канала, см. категория 5). VK-доля и дрейф-доля — не чинятся (вне Telega / другой слаг). Truly-lost доля = индикатор «деньги без размеченного результата», лечится только разметкой на стороне закупки. Кодом не чинится без риска ложных матчей.

### 4. orphan-заявки после мая (лид есть, заказа нет) — потерянные заявки

- **Что это / симптом.** **Единственная категория с НАСТОЯЩЕЙ потерей из воронки.** Посевной лид после мая существует в `local_leads_all`, но в `big_analytics_full` строки нет — потому что воронка после мая строится ОТ ЗАКАЗА (см. §0): несматченная заявка не порождает строку даже с `cost=0`. Вкладка `orphans_заявки_после_мая` (рекомендация: переименовать в `потерянные_заявки_после_мая`).
- **Возможный масштаб.** **56-60 лидов на 14-15 метках** (граница дрейфует с прогонами), `00000000` ровно 2, реальная дата 54, **продаж 1** (krasnodar_i_kraj_max / avtoworld-kuban.ru), визитов 6. Подкатегории: **E** = заказа нет совсем (≈26 л / 6 меток); **B** = заказ есть, но по другому `utm_content` (14 л / 4 метки); **D** = заказ на другом домене (1 л). Топ-метки: tipichnyj_krasnodar_krasnyj_flag_max/avtoworld 12 л; bashkiriya_online_max/havaldrive-102 11 л; chp_kuban_max/avtoworld 10 л.
- **Как проверять:**
```sql
-- посевные лиды после мая, отсутствующие в витрине (нет заказа по 5-полевому ключу)
WITH posev AS (
  SELECT l.id, lower(trim(ld.name)) AS domain, l.utm_campaign,
         lpad(btrim(l.utm_content),8,'0') AS content,
         lower(btrim(l.utm_source)) AS src, lower(btrim(l.utm_medium)) AS med, l.status
  FROM local_leads_all l JOIN local_domains ld ON ld.id=l.domain_id
  WHERE l.utm_medium='posev' AND l.created_date >= '2026-05-01'
    AND coalesce(l.utm_campaign,'')<>''
    AND coalesce(l.source_name,'') NOT LIKE 'LeadV%'
    AND coalesce(l.source_name,'') NOT IN (SELECT pixel_name FROM local_pixel_config)
), orders AS (
  SELECT effective_domain AS domain, utm_campaign,
         lpad(btrim(utm_content),8,'0') AS content,
         lower(btrim(utm_source)) AS src, lower(btrim(utm_medium)) AS med
  FROM local_telega_in_orders WHERE status='complete' AND created_at>='2026-05-01')
SELECT count(*) AS lost_leads, count(DISTINCT (p.domain,p.utm_campaign)) AS labels
FROM posev p
WHERE NOT EXISTS (SELECT 1 FROM orders o
  WHERE o.domain=p.domain AND o.utm_campaign=p.utm_campaign AND o.content=p.content
    AND o.src=p.src AND o.med=p.med);  -- ⇒ ~56 lost (556 всего, 500 matched)
```
- **Как понять РЕАЛЬНАЯ ли это потеря.**
  - **Подкатегория B** (заказ есть по другому `utm_content`) — **зеркало категории 2** (расход на пост X, лид с поста Y). НЕ полная потеря результата как факта, но лид физически выпал из строки витрины. Спорная: by-design асимметрия осей.
  - **Подкатегория E** (заказа нет совсем) — лиды с поста без закупки через Telega (органика/другой канал) ИЛИ закупка не доехала в `local_telega_in_orders`. Если VK-метка → НЕ потеря FDW (Telega VK не закупает). Если telegram/max-метка без заказа → реальная потеря заявки из воронки.
  - **Критерий РЕАЛЬНОЙ потери:** лид валиден (не LeadV, не pixel), `utm_source` ∈ telegram/max, и его в `big_analytics_full` нет → потеря из воронки независимо от наличия заказа (важна заявка, не деньги). Именно эти 56 — реальная потеря заявок.
- **Как решить.** **Чинится кодом.** Достроить витрину посевов после мая лид-онли строками (`cost=0, kol_vo>0`) для заявок без заказа — UNION в `load_telega_in_orders.py` / `load_crop_to_big_analytics.py` (по аналогии с `_add_social_posev`). Риск: golden 47 не должен сдвинуться (посевы ≠ Кудерко-Авто-директ), но 1 продажа добавится в воронку посевов → проверить инвариант `korr ≥ kval ≥ priezd ≥ prodazhi` и golden-gate. Обязательно исключить пересечение с уже учтёнными (анти-задвоение).

### 5. дрейф слага канала — нормализация разметки

- **Что это / симптом.** Один и тот же канал/пост размечается разными слагами: `obychn_stvrp` vs `obychnyi_stvrp`, `zhv_news_vlg` vs `zhv_novosti_vlg`/`zhv_zhest_vlg`, `zelenodolsk_lfe` vs `zelenodolsk_life`; `max` vs `telegram` у одного канала; VK-метки без закупки в Telega. Из-за дрейфа метка лида не сходится с меткой расхода/реестра — корень категорий 2, 3 и части 1.
- **Возможный масштаб.** Качественный: проявляется в 11 связках «37 зря» (raw-вариант слага в `account_leads`, но не в реестре `account`), в max/tg-метках категории 3, в `krasnodar_i_kraj_max`(лид) vs `krasnodar_i_kraj`(заказ, telegram) — другой слаг И другой src.
- **Как проверять:**
```sql
-- близкие слаги на одном домене (кандидаты на дрейф): группировка по нормализованному слагу
WITH labels AS (
  SELECT DISTINCT lower(trim(ld.name)) AS domain, l.utm_campaign
  FROM local_leads_all l JOIN local_domains ld ON ld.id=l.domain_id
  WHERE l.utm_medium='posev' AND coalesce(l.utm_campaign,'')<>'')
SELECT domain,
       -- нормализация: убрать _vk/_max суффикс, схлопнуть транслит-варианты
       regexp_replace(utm_campaign,'(_vk|_max)$','') AS base_slug,
       array_agg(DISTINCT utm_campaign) AS variants, count(DISTINCT utm_campaign) AS n
FROM labels GROUP BY 1,2 HAVING count(DISTINCT utm_campaign) > 1 ORDER BY n DESC;
```
- **Как понять РЕАЛЬНАЯ ли это потеря.** Дрейф сам по себе = **причина** потерь категорий 2-4, не отдельная потеря. Реальная потеря возникает, когда дрейф разводит расход и лид по разным строкам/слагам так, что лид выпадает из витрины (категория 4) или расход теряет привязку (категория 3). VK-суффикс — НЕ дрейф к Telega (категория 8). Различать: `_vk` → вне Telega; транслит-варианты одного base_slug на одном домене → дрейф, чинится словарём.
- **Как решить.** **Процесс + данные:** единый словарь нормализации слагов (расширить `gsheets_crop_targeting_account_pravilo_utm` или добавить канонизацию `utm_campaign` на входе step0/step3). Кодом — точечно, с риском схлопнуть разные реальные кампании (нужна ручная вычитка кандидатов из запроса выше). Не автоматизировать без ревью. golden-gate после.

### 6. коллизия UTM между доменами — корень хрупкости #1

- **Что это / симптом.** Одна и та же UTM-метка встречается на нескольких доменах. Поскольку `pravilo_utm` не знает домена (категория 1), глобальный `NOT IN`/матч по метке без домена ловит чужие домены.
- **Возможный масштаб.** **82 метки posev-лидов на > 1 домене + 204 метки реестра `account` на > 1 домене.**
- **Как проверять:**
```sql
-- метки лидов-посевов, встречающиеся на >1 домене
SELECT l.utm_campaign, count(DISTINCT lower(trim(ld.name))) AS domains,
       array_agg(DISTINCT lower(trim(ld.name))) AS domain_list
FROM local_leads_all l JOIN local_domains ld ON ld.id=l.domain_id
WHERE l.utm_medium='posev' AND coalesce(l.utm_campaign,'')<>''
GROUP BY 1 HAVING count(DISTINCT lower(trim(ld.name))) > 1
ORDER BY domains DESC;  -- ⇒ 82 метки
-- аналогично для реестра: gsheets_crop_targeting_account по "utm утвержденная" ⇒ 204
```
- **Как понять РЕАЛЬНАЯ ли это потеря.** Сама коллизия — **уязвимость, не потеря**. Реальной потерей становится только в связке с категорией 1: глобальный `NOT IN` по коллизионной метке вырезает лид на «не своём» домене. Критерий реальной потери: метка коллизионна (domains>1) И вырезана `NOT IN` И на своём домене утверждена И не учтена другой веткой. На текущих данных все такие после-применения сводятся к «37 зря» (до мая → задвоение, см. категория 1).
- **Как решить.** **Кодом** (структурно): добавить домен в ключ матча везде, где сейчас матч по голой метке — `pravilo_utm` использовать только как мост UTM↔утверждённая, а включение/исключение строить через `NOT EXISTS` с JOIN по `Сайт`/домену (как `_add_social`). Это устраняет корень категории 1. Риск задвоения (см. категория 1) — обязательная проверка пересечения веток + golden-gate.

### 7. таймзоны MSK/Екб на границе суток — потерь НЕТ (детектор на будущее)

- **Что это / симптом.** Опасение: заказ/лид у полуночи 30.04↔01.05 может перескочить через границу мая из-за разницы MSK (+3, таблица) и Екб (+5, мак) → попасть не в ту ветку воронки (gsheets до мая vs api после мая).
- **Возможный масштаб.** На данных — **0**. В окне границы мая ±3ч от полуночи заказов нет; 0 заказов после мая с датой поста (`utm_content`) до мая → граница чистая.
- **Как проверять (детектор-сторож на будущее):**
```sql
-- заказы у самой границы мая (опасная зона смещения суток ±3ч)
SELECT id, order_id, created_at, utm_content, utm_campaign,
       (created_at AT TIME ZONE 'Europe/Moscow') AS msk,
       (created_at AT TIME ZONE 'Asia/Yekaterinburg') AS ekb
FROM local_telega_in_orders
WHERE created_at BETWEEN '2026-04-30 21:00:00' AND '2026-05-01 03:00:00'
ORDER BY created_at;  -- ⇒ ожидаем 0 строк
-- + перекрёстная: заказ после мая с utm_content (датой поста) ДО мая
SELECT count(*) FROM local_telega_in_orders
WHERE status='complete' AND created_at >= '2026-05-01'
  AND utm_content ~ '^[0-9]{8}$' AND utm_content <> '00000000'
  AND to_date(utm_content,'DDMMYYYY') < '2026-05-01';  -- ⇒ ожидаем 0
```
- **Как понять РЕАЛЬНАЯ ли это потеря.** Реальная потеря/задвоение = если детектор вернёт > 0 строк И эти заказы попали в неправильную ветку (заказ с MSK-датой 01.05 обработан как до-майный или наоборот). Сейчас 0 → потерь нет. Запускать детектор после каждого прогона как регресс-сторож.
- **Как решить.** Если детектор сработает: зафиксировать зону явно — границу мая резать по одной канонической зоне (зона данных Telega = MSK), `created_at` приводить `AT TIME ZONE 'Europe/Moscow'` перед сравнением с `2026-05-01`. Пока — мониторинг, правок не требуется.

### 8. VK-метки — органика, НЕ потеря

- **Что это / симптом.** Посевные лиды с VK-метками (`*_vk*`), под которыми в Telega нет заказов. Выглядит как «расход без заявок» или «заявка без расхода» в зависимости от вкладки.
- **Возможный масштаб.** Качественный: в категории 3 — 3 VK-метки на avtoworld-kuban.ru (avtorynok_krasnodar_prodazha_vk, avtorynok_krasnodar_vk, chp_krasnodar_novosti_vk); в категории 4 — часть подкатегории E.
- **Как проверять:**
```sql
-- источники в заказах Telega: VK там быть не должно совсем
SELECT lower(btrim(utm_source)) AS src, count(*) AS orders
FROM local_telega_in_orders WHERE status='complete' AND created_at>='2026-05-01'
GROUP BY 1 ORDER BY orders DESC;
-- ⇒ telegram 702 / max 540 / '' 234 / m 1 / yandex 1 ; VK = 0
-- VK-метки среди посевных лидов (для понимания объёма органики)
SELECT count(*) FROM local_leads_all
WHERE utm_medium='posev' AND lower(utm_source) LIKE '%vk%' AND created_date>='2026-05-01';
```
- **Как понять РЕАЛЬНАЯ ли это потеря.** **НЕ потеря FDW by-design.** Telega.in **VK не закупает совсем** (orders src VK = 0). Значит VK-лид = органика VK-поста или закупка VK другим каналом/вручную → расхода в Telega быть НЕ должно, и матч заказ↔лид по VK невозможен в принципе. Критерий: `utm_source` лида содержит `vk` И в `local_telega_in_orders` нет ни одного VK-заказа (всегда так) → это органика, исключить из «потерь Telega».
- **Как решить.** Не чинится в FDW-ветке. Процесс: если VK-посевы нужно учитывать как канал — это отдельная ветка `_add_social_posev` (VK/Max), а не Telega. VK-расход (если есть) приходит из другого источника, не `local_telega_in_orders`. В рамках Telega-оси — пометить «органика/вне Telega», не считать потерей.

### 9. пустой «Канал» в листе лидов → CampaignName-сирота (внедрено 2026-06-11)

- **Что это / симптом.** В листе лидов (`public.gsheets_crop_targeting_account_leads`) у части посевных строк колонка **«Канал» пустая**. `step3._build_crop_sql` проецирует «Канал» → `CampaignName`, поэтому такие строки приходят в витрину `big_analytics_full` с **пустым `CampaignName` и NULL `поставщик`** → в матрице PBI сливаются в одну безымянную строку «сироту» (расход у них NULL — это лид-сторона). На момент внедрения: **274 строки листа / 737 заявок** с пустым «Каналом» (в витрине ~253 строки / ~702 заявки — после дедупликации/границ).
- **Возможный масштаб.** 737 заявок без канала. Из них (read-only сверка с листом закупов `gsheets_crop_targeting_account` по `TRIM("utm утвержденная")`, покрытие utm = 100%): **~657 заявок имеют однозначный канал** (ровно 1 distinct непустой «Канал» на utm); с дата-гардом ±7 дней восстановимо уверенно **~565 заявок** (L1 utm+Сайт ≈188 + L2 utm ≈377); **~172 заявки уходят под лейбл** (несколько каналов на utm, либо лид раньше первого закупа >7 дней — подозрительно).
- **Правило восстановления (каскад, внедрено в `step3._build_crop_sql`):**
  - **L1** — матч лида к закупу по `(TRIM("utm утвержденная"), LOWER(TRIM("Сайт")))`, восстанавливаем «Канал» **только если ровно 1 distinct непустой «Канал»** на ключе.
  - **L2** — иначе матч только по `TRIM("utm утвержденная")`, тоже **только при однозначном канале** (1 distinct).
  - **Дата-гард (L1/L2):** дата лида `>= min(дата закупа с этим utm) − INTERVAL '7 days'`. ±7 дней — допуск на лиды чуть раньше формального старта закупа (настройка/тест); лид раньше первого закупа >7 дней не восстанавливаем (подозрителен).
  - **Только однозначный канал:** несколько каналов на один utm = неоднозначно, наугад не приписываем.
  - **Лейбл:** невосстановимое → `CampaignName = '(посев: канал не определён)'` (НЕ NULL/пустая строка — иначе в PBI снова безымянная сирота, а `SURROGATE-CAMPAIGN-FIX` в `build_star` назначает суррогатный ключ только непустым именам).
  - `поставщик` (`«Тип закупа»`) восстанавливается тем же каскадом при однозначности; невосстановимый остаётся **NULL** (не ключевое поле, лейбл не нужен).
  - **Существующий непустой «Канал» НЕ перезаписывается** (он первый аргумент COALESCE; read-only-проверка: **0 строк**, где каскад дал бы другой канал при уже заполненном).
- **Как понять РЕАЛЬНАЯ ли это потеря.** Это не потеря строки из воронки (строка есть, метрики целы), а **потеря разреза по каналу**: заявка не разнесена по конкретному посевному каналу. Суммы воронки (заявки/korr/priezd/prodazhi) от фикса НЕ меняются — меняется только разнесение по `CampaignName`/`поставщик`. Golden Кудерко не затрагивается (gsheets-посевы, расход у лид-строк NULL; Кудерко-срез = direct/Контекст).
- **Как решить.** Код (каскад выше) восстанавливает однозначное; остаток — **процесс**: менеджеры дозаполняют «Канал» в листе лидов. Сигнал для этого — data-quality issue `crop_empty_channel` в step8 (`_check_and_report_crop_empty_channel`, постит на дашборд кол-во строк/заявок + примеры utm).
