## 1. Цель и границы

**Цель.** Перенести расчёт аналитики из PostgreSQL в ClickHouse, сделав его быстрее и проще:
убрать промежуточные материализованные таблицы, убрать инкрементальные окна-костыли, получить
возможность считать сверки на десятках миллионов строк без таймаутов.

**Что НЕ входит в задачу:**

- Удаление чего-либо в PostgreSQL. v5 продолжает работать, ничего не сносим.
- Изменение бизнес-логики. v6 должен воспроизвести цифры v5, а не «улучшить» их.
  Любое расхождение — дефект v6, пока не доказано обратное.
- Incremental refresh в Power BI — запрещён, как и в v5.

**Критерий приёмки проекта.** Расход, заявки, приезды и продажи в v6 сходятся с v5
на общем периоде в пределах погрешности округления. Расхождение по любой метрике —
блокер, а не «особенность».

## 3. Архитектура слоёв

Ключевое решение Семёна: **итоговые слои — вьюхи, промежуточные таблицы не материализуются.**

```
raw_data.*  (таблицы, загружаются извне)
    │
    ├─► ad_analytics.v_sources     VIEW   (step3 + corrections + step6 слиты)
    │        │
    │        ├─► ad_analytics.v_pixel_score   VIEW   (step11)
    │        │        │
    │        │        └─► ad_analytics.v_arrival   VIEW   (step13)
    │        │                 │
    │        │                 └─► ad_analytics.fact_big_analytics   VIEW  (unified + звезда)
    │        │                          │
    │        │                          └─► pbi_big_analytics_full   VIEW  (для Power BI)
    │        │
    │        └─► ad_analytics.Dim_*   VIEW   (Campaign, AdGroup, Date, Site, Adjustment, Location)
    │
    └─► ad_analytics.arp   REFRESHABLE MATERIALIZED VIEW  (REFRESH EVERY 1 WEEK)
```

### 3.1 Реестр объектов и их типы

| Объект | Тип в CH | Обоснование |
|---|---|---|
| `raw_data.*` | таблицы | сырьё, приходит извне |
| `big_analytics_direct / full / seo / pixel / crop / reviews / unified` | **не создаются** | в v5 это UNLOGGED-буферы, 0 строк между прогонами, вьюх над ними нет, единственный потребитель — факт. Растворяются в CTE. |
| `Dim_Campaign / AdGroup / Date / Site / Adjustment / Location` | `VIEW` | мелкие, пересчёт дёшев |
| `fact_big_analytics` | `VIEW` | решение Семёна |
| `pbi_big_analytics_full` | `VIEW` | точка подключения Power BI; здесь же резать окно |
| `arp` (площадки) | `REFRESHABLE MV`, `REFRESH EVERY 1 WEEK` | обновляется раз в неделю, атомарная подмена |
| `campaign_status` | **таблица** | результат вызова Grid API, в SQL невыразим |

### 3.2 Глубина вложенности

Схема «один шаг = одна вью» даёт 6 уровней. Сжимается до **4 вью**:

1. `step3 + corrections + step6` → одна вью (разделить нельзя: corrections меняет таблицы
   step3 «на месте», а в ClickHouse нет `UPDATE`)
2. `step11` (pixel score)
3. `step13` (arrival)
4. `unified + fact`

Внутри первой — цепочка примерно из 12 CTE. Глубже не дробить: в ClickHouse глубокая
вложенность вью ломает pushdown предикатов.

### 3.3 Риск, принятый осознанно

Power BI работает в import-режиме и на каждом refresh прогоняет всю цепочку заново.
Смягчение: резать окно в `pbi_big_analytics_full`, не углублять вложенность.
Решение обратимо одной DDL-командой — `fact_big_analytics` превращается в
`REFRESHABLE MATERIALIZED VIEW` без изменения схемы и кода-потребителя.

## 5. Спецификация ARP (площадки)

Отдельная таблица, полный пересбор раз в неделю.

### 5.1 Что меняется против v5

| | v5 | v6 |
|---|---|---|
| Реализация | таблица, инкремент окном `MAX(date) − 61 день` | `REFRESHABLE MV`, `REFRESH EVERY 1 WEEK`, полный пересбор |

### 5.2 Сборка

Источник — `raw_data.yandex_direct_report_rows`.

**Уникального бизнес-ключа нет.** Измерено:

| Ключ | Distinct | Дублей |
|---|---|---|
| `row_key` | 23 681 851 | 0 |
| базовые 6 полей | 9 577 257 | 14 104 594 |
| 10 полей (+ device, criterion_id, loc_pres_id, ad_format) | 22 828 515 | 853 336 |

Остаточные 853 336 — SEARCH-строки с `ad_group_id IS NULL` и `criterion_id IS NULL`:
API отдаёт несколько строк с одинаковыми измерениями и разными `row_key`.

🛑 **`ReplacingMergeTree` не применять** — он схлопнет эти строки до одной и потеряет клики
и расход. Только `GROUP BY` шести измерений + `SUM()` по метрикам.

Гранулярность: `date × domain × campaign_id × ad_group_id × ad_network_type × placement`.

### 5.4 29 колонок обогащения

Атрибуция кампании (17) — regex по `CampaignName` + join на `gsheet_sites` по домену:

шаблон, тип_сайта, статус, key, key2, placement_key`.

CRM-воронка (12) — join по `key2 = created_date|campaign_id|group_id|placement_key`

Выкинуть при переносе: `направление` (дубль `site_quiz`), `тип_заявки` (константа `'Заявки'`).

| Дата | Метрика | ARP | raw CH | Δ |
|---|---|---|---|---|
| 2026-05-01 | clicks | 78 561 | 79 267 | +0.90% |
| 2026-06-01 | clicks | 196 983 | 200 267 | +1.67% |

## 6. Правила преобразования

### 6.1 corrections — правила последовательно-зависимые

Независимыми `CASE` не выражаются. Две цепи, порядок обязателен
(`corrections.py:1882-1915`):

- **campaign_code:** `0a → 0b → 0d → 0c → 6`
- **adgroup_code:** `2 → 3 → 5 → 4 → 4б`

Правило 3 читает `AdGroupName`, уже изменённое правилом 2; правило 4 читает `adgroup_code`
после 3 и 5; правило 0c — после 0a, 0b, 0d.

Независимы только правила 1/1б/1в/1г (поле «специалист») — чистые
`CASE WHEN account_login IN (...) AND Date < threshold`.

**Реализация в CH:** вложенная цепочка CTE, каждое правило = отдельный уровень. `UPDATE` нет.

### 6.2 Дробная пиксельная атрибуция

`step11_pixel_score/step11.py:245-258`:

```
weight = cpl_score / NULLIF(SUM(cpl_score) OVER (PARTITION BY month, салон, domain), 0) * 100.0
атрибуция = pixel_domain_value × weight / 100
```

Дробь несут: `kol_vo_zayavok, korr, kval, priezd, prodazhi`.

🛑 **Категорически запрещено приводить к целому.** Задокументированный эффект
(`build_star.py:555`): `::integer` превратил приезды пикселя **6097 → 1614**.

В ClickHouse — `Decimal`, не `Int`. Типы во вьюхах фиксировать **явно**
(`toDecimal64(x, 2)`): CH выводит типы из выражения, и они поедут при любой правке запроса.
Именно этот класс ошибки дал `PBI_NUMERIC_OVERFLOW_2026-07-28` — 136 993 строки приехали
в Power BI с `total_cost = NULL`.

### 6.3 Оконные функции — точки риска

| Место | Конструкция | Статус в CH |
|---|---|---|
| `step11.py:248` | `SUM(cpl_score) OVER (PARTITION BY month, салон, domain)` | поддерживается |
| `step13.py:781` | `LEAD(d) OVER (PARTITION BY dom ORDER BY d)` | поддерживается |
| `step13.py:894-895, 930-931` | `SUM(SUM(x)) OVER (...)` — агрегат под окном | **требует переписывания** через отдельный CTE, не верифицировано |

### 6.4 Прочие обязательные фильтры

- `is_copy_for_removal` — фильтровать явно в raw-leads потребителях, где это правило включено
  по оси/источнику. Спец-дедуп `Лидер` crmf→mauto в `step3` удалён 2026-08-19 ради BA5-паритета
  заявочной оси; не подменять им общий флаг.
- Суррогатные ключи: `hashtext` (PG) → `cityHash64` (CH).
- `DISTINCT ON` (PG) → `argMax` или `row_number()`.
