## 1. КАРТА ВОЗМОЖНЫХ ПОТЕРЬ — где посевная заявка выпадает из big_analytics_full

Две независимые оси посевов (подтверждено кодом):
- **ВОРОНКА** (направление=посевы в `big_analytics_full`): `step10_crop_targeting/load_crop_to_big_analytics.py`,
  два источника по дате — gsheets `< 2026-05-01` (L222) и API `>= 2026-05-01` (L233).
- **РАСХОД/ЗАКАЗЫ**: `step10_crop_targeting/load_telega_in_orders.py` из `local_telega_in_orders`
  (только после мая, 1 строка = 1 заказ telega).

Точки потери (P1…P8), по каждой — какой класс заявок выпадает:

### P1 — ПОСЛЕ МАЯ: витрина строится ОТ РАСХОДА (корневая, доказана) 🔴
`load_telega_in_orders.py`: `FROM tio_dated d` (=`local_telega_in_orders`, 1 строка=1 ЗАКАЗ)
`LEFT JOIN LATERAL leads_agg` по **5-полевому ключу** (домен + utm_campaign +
`lpad(btrim(utm_content),8,'0')` + utm_source + utm_medium). Метрики лида = `COALESCE(l.kol_vo_zayavok,0)`.
- Строка в `big_analytics_full` СОЗДАЁТСЯ от ЗАКАЗА; лид только ПРИКЛЕИВАЕТСЯ.
- **Класс потери:** посевная заявка, по которой НЕТ заказа telega на тот же 5-полевой ключ
  (заявка с поста без закупки через telega.in / органика / закупка другим каналом / другой
  `utm_content` поста / заявка не доехала в `local_telega_in_orders`).
  Такая заявка НЕ порождает строку вообще — даже с `cost=0`. **Полная потеря из воронки.**
- Масштаб (read-only): 556 посев-лидов после мая → 500 сматчены, **56 теряются** (14 меток, 1 продажа).

### P2 — ПОСЛЕ МАЯ: жёсткость ключа utm_content (подкласс P1)
`lpad(btrim(utm_content),8,'0')` — равенство по дате поста. Лиды с `utm_content='00000000'`
(дата поста потеряна при разметке) НИКОГДА не сматчатся с заказом, у которого реальный
`utm_content=DDMMYYYY`.
- **Класс потери:** валидный лид с `utm_content=00000000`, по которому есть расход с реальной
  датой поста → лид выпадает (а расход уходит в orphans_расход как норма).
- Контраст: ДО мая `utm_content` в матче НЕ участвует (P5), там 00000000 безвреден.

### P3 — ДО МАЯ: nearest-prior placement (gsheets-ветка) ⚠️ низкий риск
`load_crop_targeting_leads.py`: лид матчится к размещению по 3 ключам — utm_campaign (через мост
`pravilo_utm`), домен=Сайт, дата `placement_date <= created_date AND delta <= 90 дн`,
`DISTINCT ON(lead_id) ORDER BY placement_date DESC`.
- **Класс потери:** лид, для которого на его домене НЕТ ни одного размещения с
  `placement_date <= created_date` в окне 90 дней (например, заявка раньше первого размещения,
  или размещение позже заявки, или дельта > 90 дн). Лид не находит placement → выпадает.
- Также: метка лида НЕ разрешается через мост `pravilo_utm` (P6) → нет `utm_effective` → нет матча.

### P4 — Фильтры posev_leads_raw: LeadV / pixel / пустой utm_campaign (НОРМА, но проверить границу)
`step3.py` отбор посев-лидов исключает: `source_name` LeadV-поставщика, pixel
(`utm_source LIKE 'victory_%'`), пустой `utm_campaign`.
- **НОРМА**, если отсекается мусор. **РИСК потери**, если осечка фильтра режет валидный лид
  (например, легитимный лид с пустым `utm_campaign`, или ложное срабатывание LeadV-детекта).
- Класс потери: валидная заявка, ошибочно классифицированная как LeadV/pixel/пустая.

### P5 — Отсечки по дате (граница мая)
gsheets-ветка `< 2026-05-01`, API-ветка `>= 2026-05-01`. Заказ датируется `created_at` (дата
размещения в telega), не датой заявки.
- **Класс потери (теоретический):** заявка на стыке периодов, если её источник-строка попала не в
  ту ветку. Проверено ранее: 0 заказов в окне границы ±3ч от полуночи (TZ MSK/Екб) → потерь на
  границе суток НЕТ. Оставляю как точку мониторинга (при изменении границы).

### P6 — Мост pravilo_utm: метка не в справочнике 🔴 (корень хрупкости #1)
`pravilo_utm` (=`gsheets_crop_targeting_account_pravilo_utm`) маппит UTM → «utm утвержденная».
Справочник НЕ содержит домена — только UTM + утверждённый вариант.
- `step3.py` L972 `_add_telegram_to_crop_sql`: **голый `NOT IN (SELECT … FROM pravilo_utm)` БЕЗ
  домена** → вырезает 865 telegram-posev-лидов; из них **37 ЗРЯ** (метка есть в pravilo, но
  принадлежит ЧУЖОМУ домену; 37 лидов / 7 визитов / 0 продаж, все до мая 14.01–05.04).
  ⚠️ ВАЖНО: эти 37 НЕ потеряны из итога — они уже в воронке через gsheets-ветку
  (`gsheets_crop_targeting_account_leads`). Telegram-фикс для них = **ЗАДВОЕНИЕ** (см. §4 риск).
- Контраст: `_add_social_posev_to_crop_sql` L1126 уже `NOT EXISTS` с JOIN по домену (исправлено
  для Max/VK).
- **Класс потери:** лид, чья метка не разрешается через `pravilo_utm` на СВОЁМ домене
  (raw-вариант метки `obychn_stvrp`→`obychnyi_stvrp` и т.п. не в реестре утверждённых).

### P7 — domain_id NULL ⚠️ (НЕ глобальный фильтр — проверено)
Политика `domain_id IS NOT NULL` глобально **ОТКЛОНЕНА** (уничтожит реальный трафик; orphan-лиды
корректны by design). domain_id НЕ является фильтром включения посевов.
- **Класс потери:** маловероятен в посевах (привязка идёт по домену-строке/Сайту, не по domain_id),
  но мониторить: лид с `domain_id NULL` + домен не резолвится в `local_domains` → может выпасть из
  агрегата `leads_agg` (JOIN `local_domains` по `LOWER(TRIM(name))`).

### P8 — Социальный путь _add_social_posev (Max/VK)
`_add_social_posev_to_crop_sql` L1126: `NOT EXISTS (gsheets_crop_leads JOIN pravilo_utm по
domain+utm)`. Уже domain-aware.
- **Класс потери:** VK-метки — telega.in VK НЕ закупает совсем (`local_telega_in_orders` src=vk → 0
  заказов). VK-заявки с поста = органика/закупка другим каналом, расхода в telega быть не должно →
  это НЕ потеря FDW, но лид может не иметь строки расхода (cost=0). Если VK-лид валиден и не попал
  в воронку даже с cost=0 → потеря по природе P1.

## 2. КАК ПРОВЕРЯТЬ — SQL-инварианты (reusable, прогонять регулярно)

Главный инвариант: **«всего валидных посевных заявок» == «учтённых заявок в big_analytics_full»**.
Дельта = потери.

> ⚠️ Грабли (из практики, учесть при написании запросов):
> - `big_analytics_full` НЕТ колонки `utm_campaign` (она внутри `CampaignName`/`номер|название`);
>   заявки = `kol_vo_zayavok`. Домен = `SPLIT_PART(аккаунт|сайт,'|',2)`.
> - pgq.py на Victory печатает ТОЛЬКО последний SELECT → по одному запросу; кириллица → `.sql`+scp.
> - `account_leads.Дата` = TEXT `DD.MM.YYYY` → `to_char`/`to_date` для сравнения.

### Инвариант I0 — общий счётчик потерь (после мая)
```sql
-- Всего валидных посев-лидов после мая (критерий = как в posev_leads_raw)
WITH posev AS (
  SELECT l.id, l.utm_campaign, l.utm_content, LOWER(TRIM(l.domain)) AS dom,
         l.utm_source, l.utm_medium, l.created_date
  FROM local_leads_all l
  WHERE l.utm_medium = 'posev'
    AND l.created_date >= '2026-05-01'
    AND l.utm_campaign IS NOT NULL AND TRIM(l.utm_campaign) <> ''
    AND COALESCE(l.source_name,'') NOT ILIKE '%LeadV%'      -- не LeadV
    AND l.utm_source NOT LIKE 'victory_%'                   -- не pixel
),
matched AS (  -- сматченные = есть заказ telega по 5-полевому ключу
  SELECT DISTINCT p.id
  FROM posev p
  JOIN local_telega_in_orders o
    ON o.status='complete'
   AND LOWER(TRIM(o.utm_campaign)) = LOWER(TRIM(p.utm_campaign))
   AND lpad(btrim(o.utm_content),8,'0') = lpad(btrim(p.utm_content),8,'0')
   AND LOWER(TRIM(o.utm_source)) = LOWER(TRIM(p.utm_source))
   AND LOWER(TRIM(o.utm_medium)) = LOWER(TRIM(p.utm_medium))
   -- домен заказа: post_links jsonb->>0 host / order_project_name (см. effective_domain в коде)
)
SELECT
  (SELECT COUNT(*) FROM posev)                              AS vsego_posev_zayavok,
  (SELECT COUNT(*) FROM matched)                            AS uchteno_v_vitrine,
  (SELECT COUNT(*) FROM posev) - (SELECT COUNT(*) FROM matched) AS poteryano;
-- Эталон на 2026-06-08: 556 / 500 / 56
```

### Инвариант I1 — разбивка потерь по причине (после мая)
```sql
-- Для каждой потерянной метки: есть ли заказ telega на домене+кампании ВООБЩЕ (любой utm_content)?
--   zakaz_est=False -> закупки нет совсем (заявка с поста/органика/др.канал/не доехала)
--   zakaz_est=True  -> заказ есть, но по ДРУГОМУ utm_content (зеркало orphan-расхода = P2)
-- Группировать потерянные (posev MINUS matched) по (utm_campaign, домен), считать лиды/визиты/продажи,
-- джойнить флаг наличия заказа на домене+кампании. Выгрузка = содержимое вкладки потерянные_заявки.
```

### Инвариант I2 — период до/после мая (контроль обеих веток)
```sql
-- ДО мая (gsheets nearest-prior): посев-лиды created_date < 2026-05-01, прошедшие posev_leads_raw,
--   у которых НЕТ строки в gsheets_crop_targeting_account_leads (не нашли placement в окне 90д
--   ИЛИ метка не разрешилась через pravilo_utm). Эталон ловит класс P3/P6.
```

## 3. КАК ПОНЯТЬ: РЕАЛЬНАЯ ПОТЕРЯ vs НОРМА

| Признак | Реальная ПОТЕРЯ | НОРМА (orphan-расход) | МУСОР |
|---|---|---|---|
| Есть валидный лид (не LeadV/pixel, с меткой)? | ДА | нет (только расход) | лид есть, но отсечён осознанно |
| Есть строка в big_analytics_full (заявка или cost=0)? | НЕТ | да (cost>0, kol_vo=0) | n/a |
| Источник | заявка не доехала или не приклеилась | закуплен пост без заявок | LeadV / pixel / тест / дубль |
| Действие | чинить (§4) | оставить, информативно | оставить, by design |

**Как отделить «заявка реально не доехала в исходные таблицы» от «заявка есть, но pipeline не
приклеил»** — чек для подозрительной метки:
1. **Есть ли лид?** `SELECT … FROM local_leads_all WHERE utm_campaign=… AND domain=… AND
   utm_medium='posev'` → если 0 строк → заявка не доехала в источник (проблема upstream CRM/импорта),
   не pipeline.
2. **Прошёл ли лид posev_leads_raw?** Проверить фильтры P4: не LeadV, не pixel, utm_campaign непуст,
   домен резолвится в `local_domains`. Если лид есть, но отсечён фильтром → разобрать, мусор это или
   осечка (P4).
3. **Есть ли расход/заказ telega по метке?** `SELECT … FROM local_telega_in_orders WHERE utm_campaign=…`
   на домене. Если заказа нет совсем → закупки telega не было (P1: с поста/органика/др.канал —
   обычно НЕ потеря FDW, но лид всё равно теряется из воронки если нет cost=0 строки).
4. **Почему не сматчился?** Сравнить 5 полей лид↔заказ: чаще всего расходится `utm_content`
   (00000000 vs DDMMYYYY = P2 / другой пост) либо `utm_source` (VK-лид, а telega VK не закупает = P8).

Опорные факты-калибровки (read-only, 2026-06-08):
- 14 потерянных меток после мая: 9 меток (~46 лидов) — заказа telega НЕТ совсем на домене+кампании;
  5 меток — заказ есть, но по другому `utm_content` (зеркало orphan-расхода). 1 продажа =
  `krasnodar_i_kraj_max` / avtoworld-kuban.ru.
- VK-метки (`*_vk*`): telega.in VK не закупает (0 заказов src=vk) → расхода нет by design.

## 4. КАК РЕШИТЬ — варианты фикса по классам

### Фикс A (ГЛАВНЫЙ) — достроить витрину после мая ЛИД-ОНЛИ строками 🔴 (класс P1/P2/P8)
**Идея:** для посев-заявок без сматченного заказа создавать строку `cost=0, kol_vo>0` — по аналогии
с тем, как `_add_social_posev_to_crop_sql` (step3.py L1110+) добавляет соц-посевы.
- **Где:** UNION-ветка в `step10_crop_targeting/load_telega_in_orders.py` (после основного
  `LEFT JOIN LATERAL`), ИЛИ отдельная ветка в `load_crop_to_big_analytics.py` API-части (L225+).
  Условие ветки: посев-лид прошёл posev_leads_raw, `created_date >= 2026-05-01`, и для него
  `NOT EXISTS` заказа по 5-полевому ключу → вставить строку `total_cost=0`,
  `kol_vo_zayavok = COUNT лидов`, korr/kval/priezd/prodazhi по статусам.
- **Механика (что на что влияет — ОБЯЗАТЕЛЬНО понять до правки):** новая ветка добавляет лиды и
  ОДНУ продажу в воронку посевов. Расход НЕ добавляется (cost=0) → **golden по расходу
  25 422 774.00 НЕ должен сдвинуться** (это телеграм-посевы, не Кудерко-Авто-директ; расход уже
  учтён orphan-стороной). Golden по продажам 47 — это Авто-направление Кудерко; 1 посевная продажа
  в воронку посевов добавится, но если эталон 47 считается по Авто/директу — не затронет. **Проверить
  обязательно**, не сдвинулся ли счётчик 47.
- **Риск ЗАДВОЕНИЯ (критично):** НЕ применять лид-онли к до-майным/уже-учтённым лидам. 37 telegram-
  лидов из P6 уже в воронке через gsheets-ветку — добавить их ещё раз = двойной счёт. Ветка должна
  строго `NOT EXISTS` в `big_analytics_full` (или в обоих источниках crop) для этого лида.
- **Влияние на инвариант воронки I3:** korr>=kval>=priezd>=prodazhi — лид-онли строки агрегируются
  по статусам так же, как основная ветка, инвариант сохраняется. Проверить I3 = 0 строк.

### Фикс B — telegram NOT IN → NOT EXISTS с domain-join (класс P6)
`step3.py` L972: переписать голый `NOT IN (pravilo_utm)` на `NOT EXISTS` с JOIN по домену (как
`_add_social_posev` L1126).
- **РИСК:** вернёт ~37 до-майных лидов, которые УЖЕ в воронке через gsheets → **ЗАДВОЕНИЕ**.
  ❗ Применять ТОЛЬКО с проверкой пересечения с `gsheets_crop_targeting_account_leads` /
  `crop_targeting_api_telegain_lead` (вставлять лид, только если его там ещё нет). Для до-майских
  37 лидов фикс B как есть = НЕ применять (память POSEV_FIX1: «0 однозначно к возврату»).

### Фикс C — осечки фильтров posev_leads_raw (класс P4)
Если I1/чек §3 покажет валидные лиды, ошибочно отсечённые как LeadV/pixel/пустые — уточнить условия
фильтра (например, точечный LeadV-детект по поставщику, а не по подстроке). Только после
подтверждения, что это осечка, а не мусор.

### Фикс D — до-майные потери placement (класс P3/P6)
Для лидов, не нашедших nearest-prior placement: расширить окно/проверить мост `pravilo_utm` на
raw-варианты меток (добавить недостающие соответствия в справочник). Через данные, не код.

### GATE после ЛЮБОГО фикса (обязательно, делегировать anton_sql) 🥇
1. **Golden-сверка Кудерко:** расход `25 422 774.00` и продажи `47` — до копейки/единицы.
   `Agent(subagent_type="anton_sql", prompt="golden-сверка по эталону Кудерко из GOLDEN_BASELINE.md")`.
2. **Инвариант воронки I3** = 0 строк нарушения korr>=kval>=priezd>=prodazhi (посевы).
3. **Дельта потерь I0** до/после фикса — потери должны уменьшиться ровно на класс, который чинили,
