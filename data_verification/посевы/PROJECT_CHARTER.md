# PROJECT CHARTER — Аудит и наведение порядка в посевах

> Устав проекта по домену **посевов** (crop targeting) в `big_analytics_v5`.
> Зачем затеяли, что в скоупе, как поймём что готово.
> Сопутствующие документы: [README.md](README.md) (как работает) · [AUDIT_PLAN.md](AUDIT_PLAN.md) (проблемы и план).

---

## 1. Зачем (Problem Statement)

Расход и заявки по посевам в финальной витрине `big_analytics_full` **не сходятся с первоисточниками**.
Цифры «плавают», доверия к посевной аналитике (CPL, расход по каналам) нет. Нужно разобрать поток
данных по шагам, найти все расхождения, понять какие — норма, а какие — баги, и навести порядок.

**Триггер:** при ручной сверке расход в витрине не равен сумме в Google-таблице реестра;
заявки не всегда привязаны к расходу.

---

## 2. Цель (Goal)

Добиться, чтобы по посевам выполнялись три инварианта:
1. **Расход в витрине = расход в первоисточнике** (Google Sheet до мая + Telega.in с мая), без раздувания и без потерь.
2. **Каждая посевная заявка привязана к расходу** своего канала и месяца (либо явно помечена как «без расхода»).
3. **Нет двойного учёта** расхода между источниками и между `_source_table`.

---

## 3. Модель данных (как устроено)

### Граница периодов
- **До мая 2026** (`< 2026-05-01`): расход ведётся вручную в Google-таблице → `gsheets_crop_targeting_account`.
- **С мая 2026** (`>= 2026-05-01`): расход из Telega.in API → `local_telega_in_orders` → `crop_targeting_api_telegain_lead`.
- Граница **захардкожена** в `load_crop_to_big_analytics.py` (строки 197 и 209) по столбцу `"Date"`.

### Ключевые таблицы
| Таблица | Роль |
|---|---|
| `gsheets_crop_targeting_account` | Сырой реестр расходов из Google Sheet (до мая). Колонка расхода `total_cost` (TEXT). |
| `gsheets_crop_targeting_account_pravilo_utm` | Справочник UTM: `"UTM"` (сырой) → `"utm утвержденная"` (норм. ключ). |
| `gsheets_crop_targeting_account_leads` | Расход+лиды, схлопнутые по `utm × месяц` (строит `load_crop_targeting_leads.py`). |
| `local_telega_in_orders` | Заказы Telega.in (с мая). Ключ `utm_campaign`. |
| `crop_targeting_api_telegain_lead` | Зеркало Telega.in для витрины (с мая). |
| `local_leads_all` | Все заявки. Признак посева — `utm_medium='posev'`. |
| `big_analytics_full` | Витрина. Посевы: `направление='посевы'`. |

### `_source_table` у посевов в витрине
| Значение | Что это | Расход |
|---|---|---|
| `crop_targeting` | Закупка каналов (gsheets до мая / API с мая) | есть |
| `tp8` | **Яндекс.Директ** МК/ТК кампании — НЕ закупка каналов, отдельная история (~97 млн ₽ за янв–апр) | есть (Яндекс) |
| `telegram` | Telegram-посевы (старый учёт) | есть |
| `social_посевы` | VK/Max заявки без привязанного расхода | **NULL** |

## 4. Скоуп

### В скоупе
- Сверка расхода: первоисточник → витрина, отдельно **до мая** и **с мая**.
- Матчинг заявок с расходом по UTM+месяц.
- Логика `gsheets_nearest` (подтягивание расхода из ближайшего месяца).
- Справочник `pravilo_utm` (полнота, дубли, нормализация ключей).
- Guardrail против будущих дублей (canary).
- Гигиена витрины (CPL, cost=NULL у social_посевы).

### Вне скоупа
- `tp8` (Яндекс.Директ) — отдельный домен, только не путать с закупкой каналов.
- Переписывание архитектуры пайплайна.
- Изменение источников данных (Telega.in API, Google Sheet формат).
- Заполнение Google-таблиц данными (это работа менеджера, мы только указываем что заполнить).

## 6. Найденные проблемы (реестр)

> Полный разбор с числами — в [AUDIT_PLAN.md](AUDIT_PLAN.md). Здесь — список для устава.

**Критичные (данные неверны сейчас):**
- **C1** — с мая в витрине недолито 2 033 472 ₽ (step10 не перезапускали).
- **C2** — граница 1 мая = хардкод; уже есть 1 конфликт источников.
- **C3** — `load_api_leads.py` читает несуществующую таблицу.

**До мая:**
- **B1** — ✅ ИСПРАВЛЕНО, ЗАДЕПЛОЕНО И ПРИМЕНЕНО НА ПРОДЕ (04.06.2026). `gsheets_nearest` раздувал расход витрины на +12%. Переписано на **nearest-prior** (заявка → последнее размещение ≤ её даты, окно 90 дн); расход = реестр 1:1, заявки-сироты cost=NULL; фильтр `>= 2026-01-01`. **Проверено: до мая = 9 213 650 ₽ (было 10.32M), каждый месяц = реестр.** Применено прогоном `step10_crop_targeting/pipeline.py`.

- **C1** — ✅ ЗАКРЫТО на проде (04.06.2026). Май-расход долит: **2 181 280 ₽** в витрине (был 147K) из `local_telega_in_orders`. Закрыто прогоном основного `pipeline.py` + `step10_crop_targeting/pipeline.py`.
- **B2** — 256 заявок с UTM, которых нет в справочнике `pravilo_utm`.
- **B3** — 16 заявок без `utm_campaign` («Жукова», Max).
- **B4** — 8 неоднозначных дублей в `pravilo_utm` (195 лидов).

**С мая / общее:**
- **P6** — VK/Max расход не ведётся с мая (~257 сирот).
- **P7** — `social_посевы` cost=NULL занижает CPL в 1.8×.
- **P9** — опечатки в Telega.in (`I`↔`l`, пробелы).

## 7. Критерии готовности (Definition of Done)

- [ ] **До мая:** расход витрины = расход реестра ± объяснимая дельта (логика `gsheets_nearest` либо исправлена, либо явно задокументирована и согласована как intended).
- [ ] **С мая:** расход витрины = расход Telega.in за период; step10 перезапущен, 2.03M ₽ вернулись.
- [ ] **Матчинг:** доля заявок без привязки к расходу < 5% (сейчас 25% до мая); остальные явно помечены «без расхода».
- [ ] **Guardrail:** canary-проверка встроена в pipeline и шлёт алерт при конфликте источников.
- [ ] **CPL:** отчёты по Max/VK не занижаются строками cost=NULL.
- [ ] **Документация:** README + AUDIT_PLAN + этот charter актуальны.

## 8. Риски

| Риск | Последствие | Митигация |
|---|---|---|
| Граница 1 мая — хардкод | При продлении реестра / историч. данных Telega.in → дубли расхода | canary + динамич. граница |
| Реестр Google Sheet ведётся неполно | Сироты, `gsheets_nearest` раздувает расход | дозаполнение + алерт на пропуски месяцев |
| VK/Max нет источника расхода с мая | Заявки без расхода, CPL врёт | завести источник расхода VK/Max |
| Витрина пересобирается через CTAS | Разовые замеры «плавают» | мерить после стабилизации / через guardrail |
